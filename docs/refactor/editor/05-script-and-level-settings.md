## 0. Found before slicing: saving today destroys a level's existing script

This isn't new scope §4 introduces — it's a gap phase 3 already knew about and documented at the
time (`phase3/04-slice5-playtest-settings-overwrite.md`, `01-slice2-classic-save.md`: "`MapContent`
carries no script field yet"), not a surprise. Restating it here because phase 5's entire §4 design
*depends on it being fixed first*, and its real-world consequence is more serious than "minimal
stub" makes it sound:

`MapContentWriter::write_script()` (`map_content_writer.cpp:153-157`) unconditionally overwrites
`map%05lu.txt` with a hardcoded `"REM Empty script, generated by the in-game editor.\n"` on
**every** save — `MapContent` has no script-text field at all (confirmed: nothing in
`map_content.h`, nothing read in `map_content_reader.cpp`). Open Map (phase 3 slice 4) already
lets a mapmaker open any real, shipped campaign level — which almost always has a real, non-trivial
script (confirmed against `core_files/campgns/`+`core_files/levels/`: **85%+ of real shipped
levels use the classic `.txt` script format**, only a handful use `.lua`). Opening one of those and
hitting Save today silently replaces its entire script with the empty stub.

**Done — this was slice 1**, ahead of everything else in §4 (`phase5/00-slice1-script-preservation.md`):
`MapContent` now has a `script_text` field, read verbatim in `MapContentReader` and written back
verbatim in `write_script()` (falling back to the empty stub only for a genuinely new/blank map
that never had one). Everything else in §4 — the text editor, the managed region, the
availability helper — can now be built without a save path underneath them that destroys
everything outside whatever the editor itself understands.

**Note (phase 2 wrap-up):** phase 2's own toolbox stubs for Lights/effect-emitters and Action
Points ([`02-editing-toolbox.md`](02-editing-toolbox.md) §2.8/§2.9) were never built — no
tool-strip button, no picker, no placement path — and are deliberately deferred to land here
instead, as real properties-panel work, rather than as placeholder stubs bolted onto phase 2's
simpler click-to-place tools (see [`09-toolbox-remainder.md`](09-toolbox-remainder.md) §2 for the
full punch-list entry). One piece of phase 2 plumbing is already reusable when this phase picks
up §2/§3 below: Object placement's value-property follow-up added a generic thing_idx-keyed
`PckA_EditorSetThingPosition` packet (x/y/z, `kfx_net/src/packets_cheats.c`) and edit-panel shape
(`draw_object_edit_panel()`, `kfx_editor/src/editor_toolbox.cpp`) specifically so the Light
properties panel (§2) and Action Point inspector (§3) below could reuse the same X/Y/Z editing
mechanism rather than reinventing it per-tool.

Goal: make maps *playable and authored*, not just built — level metadata, editable lights/FX,
numbered action points & hero gates, and enough script assistance that a mapmaker doesn't have
to alt-tab to a text editor for the common cases.

## 1. Level settings panel (Editor menu → Level → Settings)

**Corrected: this dialog already exists (phase 3 slice 5).** `editor_dialogs.cpp`'s
`draw_level_settings_dialog()` already has **Name**, **Players**, and **Multiplayer** — reachable
today from File > Level Settings, writing via `editor_save_level_info()` to `.lof`+`.lif`. Slice 2
(`phase5/01-slice2-level-settings-expansion.md`) added **Description** (a genuine find — the
`.lof` keyword and the `LevelInformation` struct field both already existed, just weren't wired to
anything) and a read-only **map dimensions** display. Round 4
(`phase5/03-live-test-fixes-and-texture-tools.md`) added **base texture set** and **per-slab
texture paint**. Still unbuilt: **author** (no `LevelInformation` field exists yet, unlike
description) and every script-setup-command field. **Ambient light is not being built as a
Level Settings field at all** — round 4 found it's a per-*campaign* `rules.cfg` value
(`GLOBALAMBIENTLIGHT`), not a per-level property; a Level Settings field for it would silently
affect every other level in the campaign, not just the one open — see that round's doc for the
options this leaves. The gold/max-creatures/gen-speed/pool fields depend on §0's
script-preservation fix, which is done.

Backed by map info + `.lof`/`.lif` + script setup commands. Fields:
- **Name** (done), **description** (done, slice 2) — author (→ `.lof`, not yet built — no
  `LevelInformation` field exists for it yet, unlike description).
- **Map dimensions** (done, slice 2) — chosen at New Map ([`07`](07-investigation-findings.md) F12,
  any size); read-only display after creation, straight from the live session
  (`kfx_sim_state.map_tiles_x`/`map_tiles_y`) — resizing a populated map is still deferred (things/
  APs outside bounds + `around_slab` churn).
- **Base texture set** (done, round 4) — `FeCombo` dropdown from a fixed 15-entry table mirroring
  `texture_pack_desc` (`editor_texture_packs.h`); no custom `tmap?%03d.dat` pack discovery built
  (not needed for the built-in sets to be useful — a smaller, separate follow-up if a real map ever
  needs it). Writes the one-byte `map%05d.inf`, live-previewed via `load_texture_map_file()`.
- **Per-slab texture paint** (done, round 4, v1) — a "Paint Tex" toolbox tool
  (`EdTool_PaintTexture`) that continuously LMB-drag-paints `kfx_config_state.slab_ext_data[slab]`
  directly (client-side, no undo — same accepted scope as the Stamp tool); persisted as
  `map%05d.slx`, confirmed against 99 real shipped `.slx` files. No rectangle/fill mode yet.
- **Players** (done, as a plain count) — which have hearts (derived from placed hearts, shown for
  sanity, not yet built) still to add; hero player always implicit.
- **Ambient light level** — not a per-level concept in this engine; see round 4's doc for why this
  won't be a Level Settings field as originally imagined.
- **Start gold per player**, **max creatures per player**, **generation speed** — these are
  script setup commands (`START_MONEY`, `MAX_CREATURES`, `SET_GENERATE_SPEED`). The panel
  edits them as fields and **writes them into the managed region of the script** (§4), rather
  than duplicating a config surface. **Depends on §0** — writing into a managed region only
  matters once the rest of the script actually survives a save.
- **Creature pool** — `ADD_CREATURE_TO_POOL(kind, n)` rows; also `map.pool` console command
  exists for live testing.

## 2. Lights & effect emitters

Static lights live in the sim and serialize to `.lgtfx` (phase 3). This phase adds the
place / select / edit / delete UX (toolbox stubs from phase 2 §2.8) — **confirmed still fully
unbuilt**: no Light tool entry in `editor_toolbox.cpp` today (only comments noting it as
not-started), no `PckA_EditorPlaceLight` in `packet_data.h`.

**Confirmed straightforward to build.** `light_create_light(struct InitLight *ilght)`
(`kfx_render/include/light_data.h:165`) is already public and directly callable from a new
`kfx_net` packet handler (`kfx_net` ranks above `kfx_render`, same direct-call pattern already
used for every other `PckA_Editor*` verb) — no callback-struct indirection needed, that's only for
*lower* layers reaching this. `struct InitLight` (`config.h:253-260`) is a small, five-field
struct (`radius`, `intensity`, `flags`, `mappos`, `is_dynamic`, `attached_slb`) — a new
`PckA_EditorPlaceLight(x, y)` handler just fills it from the click position and sensible defaults
and calls this one function. Same shape as `PckA_EditorPlaceObject`, not a new pattern.

- **Place light** tool: click to drop an ambient static light. New `PSt_EditorPlaceLight` +
  `PckA_EditorPlaceLight(x, y)`; the light is created in the sim's static-light list.
- **Select** (Query tool clicks a light marker) → **Light properties** panel:
  - Intensity, Radius/size, Height (original: keypad `.`/`0`, `6`/`4`, `8`/`2` before placing —
    we make them live sliders after placing), colour if the engine supports coloured static
    lights, flags (flicker etc.).
  - Live preview in the 3D view (light updates immediately).
- **Delete**: RMB on a light marker with the light tool (original: right-click).
- **Effect generators** (Lava / Drip / Portal-Ice / Dry-Ice, and any KFX effect-generator
  kinds): placed as things (they already exist as `TCls_EffectGen` / room-effect things).
  - **Place FX** tool with a kind picker; LMB-drag sets the **radius** (original behaviour).
  - Properties panel: kind, radius, spawn rate/amount if configurable.
  - These render live in the editor (particles visible) — one of the nicer WYSIWYG wins.

**Budget warnings** (from the original manual): the engine has a finite dynamic-light list and
FX cost. Show a light count / FX count with a soft cap warning in the panel and in
`verify_map()`.

## 3. Action points & hero gates

Query/zoom/reset already exist (`actionpoint.pos`, `actionpoint.reset`, `zoomto.actionpoint`,
`zoomto.herogate`); phase 4 (this session, done since this doc was first written) additionally
built the AP/hero-gate **visual marker overlay** (numbers + trigger-radius rings drawn in the 3D
view, `editor_overlay.cpp`) — non-visual query/zoom and the visual markers are both done; this
phase adds *placement* + editing, which is still the real gap.

- **Add Action Point** tool: LMB-drag from centre outward sets the trigger **radius**
  (original). New `PSt_EditorPlaceActionPoint` + `PckA_EditorPlaceActionPoint(x, y, range)`.
  `actnpoint_create_actnpoint(struct InitActionPoint*)` (`kfx_sim/include/actionpt.h:55`,
  `actionpt.c:70-79`) already exists and is directly callable the same way as `light_create_light`
  above — but **confirmed there's no `get_free_action_point_number()`-shaped helper today**
  (unlike hero gates, see below); auto-assigning "the next free number" needs a small new helper
  scanning `action_points[]`, not just a call to something that already exists.
- **Add Hero Gate** tool — **corrected: this already works today, no new code needed for
  numbering.** A hero gate is a `TCls_Object` (`object_is_hero_gate`), confirmed — but the
  original design's claim that "the editor sets its `hero_gate.number`" implies work that doesn't
  exist: `thing_objects.c:224-236` already auto-assigns a valid `hero_gate.number` via
  `get_free_hero_gate_number()` (`thing_list.c:2148`) **unconditionally, inside the generic
  object-creation path** — for *any* object with `OCtg_HeroGate` genre, created through *any*
  route, phase 2's already-shipped `PckA_EditorPlaceObject` included. Placing a hero gate today is
  already just "pick the hero-gate model in the existing object picker and click" — if that model
  doesn't yet appear in the picker's own list, that's the one small thing to check/fix, not a new
  placement verb or a new numbering mechanism.
- **Select** → inspector shows number, position, range (APs only); range editable; **renumber**
  allowed (warn if the script references the old number — cross-check §4).
- **Delete** with a confirm + script-reference warning.
- Serialize: APs → `.aptfx` (`PointNumber`/`SubtileX`/`SubtileY`/`PointRange`); hero gates →
  `.tngfx` as objects with `HerogateNumber` (phase 3).

## 4. Script editing

Full visual scripting is a **non-goal for v1** (00-overview §8). What v1 ships. **Depends on §0**
for all of it — none of this is worth building on top of a save path that discards the script.

**Format confirmed**: the classic text-command format (`IF`/`ENDIF`, `SET_GENERATE_SPEED`, etc.,
plain `.txt`) is what actually matters — **85%+ of real shipped levels** (`core_files/campgns/` +
`core_files/levels/`) use `.txt`, only a handful use the newer Lua path (`kfx_script`'s
`lua_api_*.c` family). §4's whole "editor for the classic format" framing is correct, not stale.

**No existing precedent for a multi-line text editor anywhere in this codebase** — confirmed zero
hits for `InputTextMultiline` (or anything richer) across `src/kfx_editor/`/`src/kfx_frontend/`.
This is genuinely new work, same category as phase 4's world-space overlay projection before that
slice built it.

**Recommendation for 4.1, per direct request: vendor
[ImGuiColorTextEdit](https://github.com/goossens/ImGuiColorTextEdit)** rather than build a
syntax-highlighting/line-numbered text editor from raw ImGui widgets. Checked directly:
- MIT licensed (same vendoring precedent as `tinyfiledialogs`, zlib-licensed, phase 3 slice 4) —
  a `deps/ImGuiColorTextEdit/` addition, not a build-system dependency.
- Trivial integration: exactly two files (`TextEditor.cpp`+`TextEditor.h`), no runtime
  dependencies beyond ImGui + the C++ standard library. This repo already builds at `gnu++20`
  (the library needs C++17), and already vendors ImGui 1.92.7 against the library's own
  1.92.8/1.92.9 target — close enough that breakage is unlikely, worth a quick build-and-smoke-test
  before committing to it, not assumed risk-free.
- `Render(title, size, childFlags, windowFlags)` takes an explicit size and renders as a child
  region — embeds directly into any parent ImGui window, including a resizable one (the "resizable
  message box" ask): open a normal `FeBeginModal`-style window without `ImGuiWindowFlags_NoResize`,
  call `Render("##ScriptEditor", ImGui::GetContentRegionAvail())` inside it.
- Ships a built-in `Language::Lua()` definition (useful if the Lua path ever needs the same
  editor) and documents its `Language` struct as extensible for custom languages — the classic DK
  script format (keywords like `IF`/`ENDIF`/`SET_GENERATE_SPEED`, `REM` comments) has no built-in
  definition and would need a small custom `Language` (keyword list + comment style), not a fork
  of the library itself.
- Public API is small and matches what this dialog needs directly: `SetText(string_view)`,
  `GetText()`, `SetLanguage(const Language*)`, `SetReadOnlyEnabled(bool)`.

- A multi-line text panel showing `map%05d.txt` (or `.lua`). Monospace, basic syntax tint
  (comments, commands, `IF`/`ENDIF` matching), line numbers.
- **Reload script** button: re-parse and (in playtest) re-apply. In edit mode the script is
  only parsed for validation + the helper panels, never executed.
- **Validate** button: runs the script checks from `verify_map()` §5 (balanced IF/ENDIF,
  condition count, AP/party/creature/room/spell name resolution against current config,
  undefined party refs, `WIN_GAME` presence) and lists errors with line numbers.
- Saved verbatim by `write` (phase 3) — **once §0 lands**; today it isn't.

### 4.2 Managed setup region
- The Level Settings panel (§1) and availability helper (§4.3) write into a delimited block:
  ```
  REM --- editor-managed setup: do not hand-edit between these markers ---
  ...generated SET_GENERATE_SPEED / START_MONEY / *_AVAILABLE / ADD_CREATURE_TO_POOL...
  REM --- end editor-managed setup ---
  ```
  Everything outside the markers is the mapmaker's own hand-written script, untouched. On load,
  the panels read their values back from the managed region.

### 4.3 Availability helper (Editor menu → Script → Availability)
A grid: rows = creatures / rooms / spells / doors / traps (from config), columns = per player
0–3 (+ ALL). Each cell: Off / Available / Researchable. Generates
`CREATURE_AVAILABLE` / `ROOM_AVAILABLE` / `MAGIC_AVAILABLE` / `DOOR_AVAILABLE` /
`TRAP_AVAILABLE` lines into the managed region. Mirrors `room.available` /
`creature.available` console commands, which are useful for live playtest tweaking.

### 4.4 Objective / message helper (optional, time-boxed)
Simple form → `QUICK_OBJECTIVE(n, "text", player)` / `QUICK_INFORMATION(n, "text")` /
`DISPLAY_OBJECTIVE`. Inserted at the cursor in the user region, not the managed region.

### 4.5 Creature stats
Original edited `creature.txt` in the game data dir. KeeperFX has two modern equivalents:
`SET_CREATURE_*` script commands, and a **per-map creature config layer** —
`map%05lu.creature.cfg` / `map%05lu.<name>.cfg` in the levels dir
([`07`](07-investigation-findings.md) F15). v1 stays **out of scope** for editing either; a
per-map stats panel that emits `SET_CREATURE_MAX_LEVEL` / `SET_CREATURE_STRENGTH` into the
user script region, or edits `map*.creature.cfg` directly, is a clean **v2** addition.
**Placing** custom creatures already works (§2.5) — only stat *editing* is deferred.

## 5a. Suggested slicing (not started — for when this phase begins)

Bigger than any prior phase (four real subsystems, not overlays on one), so more slices than
usual. Ordered by dependency, not by section number above:
