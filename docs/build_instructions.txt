The repository's CLAUDE.md has the full detail behind every step below.

1. Getting the code

  git clone https://github.com/edorien/keeperfx-refactor.git

The game is built with CMake. It fetches and builds its own third-party
dependencies (SDL3, OpenAL, FFmpeg, LuaJIT, curl, ...) when the system doesn't
provide them, so a machine with a C/C++ toolchain, cmake, ninja and pkg-config
can build it from scratch; the first build just takes longer.

The game needs the original Dungeon Keeper data files to run; they are not in
the repository (see docs/files_required_from_original_dk.txt).

2. Building on Linux

Needs gcc/g++, cmake, ninja and pkg-config. From the repository root:

  ./build-cmake-linux.sh

builds out/linux/daimonkeeper and copies it, with any shared libraries it
built, to dist/linux/ -- a folder you can copy to another machine. The CMake
target is called "keeperfx"; the file it produces is "daimonkeeper".

  USE_DOCKER=1 ./build-cmake-linux.sh     # same, inside an Ubuntu 24.04 container like CI

3. Building for Windows

Cross-compiled from Linux (what CI does) -- needs the MinGW-w64 i686 toolchain
(g++-mingw-w64-i686), cmake and ninja:

  KFX_OS=windows ./build-cmake-linux.sh   # out/windows/daimonkeeper.exe, dist/windows/

Natively on Windows -- from an MSYS2 MINGW32 environment with
mingw-w64-i686-{gcc,cmake,ninja}, make, git, p7zip, curl and unzip:

  extraBuildScripts\build-package-windows.bat   (from a Command Prompt)
  extraBuildScripts/build-package-windows.sh    (from a MINGW32 shell)

4. Building a package

  ./build-package.sh

builds complete, ready-to-run game folders for Windows and Linux in
dist/windows/ and dist/linux/, plus a unit-test coverage report, in one run
(SKIP_WINDOWS=1, SKIP_LINUX=1 or SKIP_COVERAGE=1 leave one out). BUILD_NUMBER
and PACKAGE_SUFFIX set the build number and suffix, e.g.

  BUILD_NUMBER=1234 PACKAGE_SUFFIX=Alpha ./build-package.sh

A release archive comes from CMake's package target, after the game data has
been staged (section 5), as CI does:

  make pkg-enginegfx pkg-assemble
  cmake --build out/windows --target package

It lands in pkg/ as daimonkeeper-<version>.<build>-kfx<compat>[-suffix].7z
(.tar.gz for a Linux build tree). The native Windows scripts in section 3 make
it too.

A package holds the game, its libraries, the game data, and LICENSE.txt,
NOTICE.txt, THIRD_PARTY_NOTICES.txt and LICENSE-graphics.txt. The first build
needs network access (dependencies, and the engine graphics repository).

5. The asset/data pipeline (make)

The Makefile no longer compiles the game; it builds the game's data. Run from
a real shell (bash; MSYS on Windows):

  make pkg-languages   # language .dat files from lang/*.po
  make pkg-gfx         # graphics .dat/.tab/.raw/.pal from PNGs
  make pkg-enginegfx   # engine graphics (clones dkfans/FXGraphics)
  make pkg-assemble    # stage configs, campaigns, levels and data into pkg/

build-package.sh runs pkg-enginegfx and pkg-assemble itself. The icon,
start-up screens and README banner are generated separately, from
res/branding/ (see its README).

6. Tests and checks

  python3 scripts/check_layering.py --strict   # library dependency order (CI-blocking)
  python3 scripts/kfx_parity.py                # content parity with KeeperFX

Unit tests (Catch2, native Linux): configure with -DKFX_BUILD_TESTS=ON and run
ctest in the build tree; see docs/Architecture/testing-harness.md.
Functional tests run inside the game: build with -DKFX_FUNCTESTING=ON and run
it with -ftests; see src/ftests/README.md.

7. Source tree layout (src/kfx_*/)

The engine is split into libraries, each a directory src/kfx_<name>/ with its
own include/ and src/, compiled as a CMake OBJECT library: kfx_platform,
kfx_config, kfx_content, kfx_model, kfx_pathfinding, kfx_sim, kfx_ai,
kfx_render, kfx_net, kfx_game, kfx_frontend, kfx_script, kfx_apploop and
kfx_editor. src/main.cpp ties them together; src/ftests/ holds the functional
tests. A library may only use libraries below it in that order -- the layering
check above enforces it.

A new source file only needs to go in the right src/kfx_<name>/src/ directory:
each library's CMakeLists.txt picks up its files by glob, for every target
(re-run cmake so it sees the new file). There is no hand-maintained file list.

The full architecture: docs/Architecture/architecture.md.
